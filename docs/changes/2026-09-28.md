# 2026-09-28 速度口径对齐 DeepSeek Harness

## 改了什么

用户调研了 `deepseek-ai/deepseek-harness` 的 token 速度计算后要求对齐。将其口径移植到本面板：

- `token_speed.py`
  - `_elapsed_ms()`：分母从"请求完整耗时（started→completed）"改回"decode 段耗时（first_token→completed）"；缺首字时间或 decode 段无效返回 0（该行不参与速度），`duration_ms` 不再兜底。
  - `calc()`：无首字时间的行不计速度（Harness 同款行为）；分子不变（output+reasoning，无回报模型走 `_est_map` 字符估算）。
  - `today_summary()`：talk_tok / talk_ms 用同一有效性条件配对（`first_token_at IS NOT NULL AND completed_at > first_token_at`），分子分母不再错配。
  - `session_stats()`：同上配对改造。
  - `avg_by_model()`：缺首字的行经 `calc` 返回 None 自动排除，docstring 更新。
  - `self_check()`：全部断言更新到 decode 口径，新增 talk_ms=3000 断言。
- Harness 参考实现：
  - `packages/session/session-stats/src/projection.ts`（decodeTokens/decodeMs 全量折叠）
  - `packages/client/ui-chat/src/client/chat/StatsPills.tsx`（tps = decodeTokens / decodeMs）
  - `packages/llm/llm/src/assistant-stream.ts`（isTokenDelta：text/reasoning/tool-call 首个 delta 即首 token）

## 为什么

- Harness 的速度 = 纯 decode 速度（首 token→完成），排队/思考由 TTFT、完整请求时间单独呈现，不揉进速度分母。
- 本面板此前（2026-09-24）为贴近体感改用完整请求分母，用户看完 Harness 对照后明确要求对齐其计算。
- 面板已有"平均首字速度"卡与每行"首字"列，等价于 Harness 的 TTFT 呈现，等待体感仍有出口。

## 生产数据验证（近 7 天 6813 行探针）

- `first_token_at` 覆盖：gpt-5.6 系缺 17~43%（多为时长更短的请求），其余模型缺 <5%；无 ft<started、无 decode≤0 异常行。
- dots 源（reasoning 立即流式）首字前耗时与是否含 reasoning 无关（2.9 vs 3.0s）→ `first_token_at` 是首 token 时刻，语义与 Harness 对齐。
- 对齐后读数示例：gpt-6-astra 389.7 t/s（decode）+ 首字 104.2s（等待单独可见）；今日均速 112.3 t/s。数字相对完整请求口径整体回升约 4~5 倍。

## 取舍与已知边界

- 与 2026-09-24 的"体感口径"冲突：按规则 4 取较新指令（对齐 Harness），旧口径待清理；等待体感改由首字列/首字卡呈现。若嫌数字虚高，回退点在 `_elapsed_ms` 一处。
- 无回报模型估算（Agnes 类）保留：其行具备 first_token_at（缺 4/856），估算 token ÷ decode 段成立；若未来某供应商连首字都不回报，该模型将无速度（Harness 同款），届时再议。
- harness 分子只有 provider outputTokens；本面板分子含 reasoning_tokens——因分母同样覆盖 reasoning 生成时段（dots 实测），且 ZCode 将两者分列，保持不变。

## 当日第二次变更：换回全请求口径（体感）+ Harness 纪律（非回滚）

用户看过 decode 口径实际数字后确认体感不符（astra 流式 187 t/s 但总耗时更长），要求换回全请求速度，并继续借鉴 Harness 设计优化全请求算法本身。

### 与 9-24 旧全请求实现的差异（借鉴 Harness 折叠器的三点纪律）

1. 分子分母同行配对：talk_tok/talk_ms、session tok/gen_ms 用同一 `started_at IS NOT NULL AND completed_at > started_at` 条件，token 只在时间有效的行上累加（旧实现分子全收、分母带兜底，存在错配）。
2. 缺时间戳不计速度：`_elapsed_ms` 只认有效墙钟对，`duration_ms` 不再兜底（Harness：无 timing → 不贡献）。
3. 无首字时间的行照常计速：全请求分母不依赖 first_token_at，gpt-5.6 系 17~43% 缺首字的行回到聚合（decode 口径会丢这些行）。

分母本身换回 `completed_at - started_at`（排队/预填充/思考/流式全在分母内 = 体感）；首字(TTFT)列与"平均首字速度"卡保留，对齐 Harness"速度与等待分开呈现"的哲学——只是本面板主数字选体感口径（用户产品决策）。

### 改动文件

- `token_speed.py`：`_elapsed_ms`（started→completed、无兜底）、`calc`、`today_summary`/`session_stats` SQL 配对条件、`avg_by_model`/`calc` docstring、头部口径说明、`self_check` 全部断言（250/50/无 ft 照计/duration 不兜底/est 30/333.3/talk_ms 4000）。

### 验证

- `py_compile` + `--self-check` → OK（含新增 duration_ms=5000 不兜底断言）
- `--once` 生产库：GLM 9.7 t/s（首字 14.3s）、astra 29.9 t/s（首字 58.3s）——体感数字与首字等待同屏可见
- 生产库 `detail_data` + 三页渲染 → 12100 字符正常，会话速度 7.0/18.9/34.0 t/s
- 近 24h 对照：astra 流式 183.8 → 全请求 50.5 t/s，GLM 35.3 → 26.3 t/s（与体感一致）
