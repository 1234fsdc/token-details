## 切换会话提速：常驻 UIA watcher（替代每秒新起 PowerShell）

- 用户要求切换会话后速度显示尽快跟着换。实测定位瓶颈：`zcode_context()` 每次探测 ~1s（进程启动+程序集加载+整树遍历），且**整树 FindAll 遍历本身在 ZCode 流式渲染时可达 12s+**（这也解释了最早的 UIA 超时成串）——push_loop 每秒一次探测，切换会话后最坏 2-3s 才换数，面板刷新也被这个 1s 探测拖住。
- 方案：常驻 PowerShell 观察进程 + Python 守护。首次全量走树后缓存标题/模型/锚点三个 UIA 元素引用，之后每 150ms 只读这 3 个元素的实时属性（~10ms，读的是最新值——会话切换/窗口拖动即时可见）；每 2s 兜底全量重走（WebView2 重渲染换掉元素引用时重建），**兜底间隔自适应**：上次走树 >3s（忙时）拉长到 15s，避免忙时连续 12s 级空走。元素引用失效（抛异常）立即触发重走。走树前先发心跳行，慢走不饿死喂狗。
- Python 侧：`_watcher_loop` 守护线程（无输出 25s 杀掉重启，指数退避；25s 是给 12s+ 慢走留的余量）+ `overlay_bind_loop` 专用绑定线程（0.3s 一拍，原 push_loop 里的粘滞/兜底/空闲归零逻辑原样迁入，db 连接线程私有）。push_loop 不再每秒起新 PowerShell，面板/详情刷新不再被探测阻塞。
- 关键坑（全部实测踩过）：① `uia_watch` 槽位的 ts 跨重启不清零 → 新进程一启动就被喂狗秒杀，PS 进程无限堆积（实测 74 个）——喂狗改用本次 spawn 私有的 `last_line` 时间戳；② `uia_last`/`overlay_anchor`/`overlay_payload` 原是 main() 局部变量，模块级 binder 线程 NameError——提升为模块级；③ 模块缺 `import threading`（原在 main 内局部导入）；④ 草稿态无标题元素时 `te` 恒 null 会让脚本每拍全量走树——归入兜底节奏。
- CacheRequest 批量缓存试过再放弃：`FindAllBuildCache` 在托管包装上不存在，Push/Pop 激活路径能把读值降到 10ms 但 FindAll 本身仍 1-1.8s（瓶颈在 provider 遍历），对忙时无解——不如元素引用快路径。
- 验证：self-check 通过（新增 `parse_watcher_line` 5 条断言：前缀剥离/anchor 容错/bytes 解码/坏行/空行归一）；试跑脚本确认快路径 ~175ms 持续输出最新标题+锚点；重启实例实拍 overlay **26.8 t/s**、定位正确、weberr.log 无新错误；watcher PS 进程 10s CPU 9%（单核，流式高峰期；空闲只有快路径，更低）。切换会话的检测延迟从最坏 ~3s 降到 ≤0.15s（元素稳定时）+0.3s 绑定拍 ≈ **~0.5s 换数**。
- ⚠️ 未验证：真实切换会话的端到端延迟需要用户亲手切（无法在不干扰 ZCode 的情况下模拟）；元素被重渲染换掉时的恢复速度（快路径抛异常→立即重走）只在诊断脚本里验证过分支，未在真实切换里观察。

## watcher 内存治理（用户问"会不会占用太大"引出，实测真超标）

- 量化：Token Details 主程序 pythonw 私有 80MB（正常）；但常驻 watcher PowerShell 跑 35 分钟涨到 **1.2GB**（物理/私有均 1.25GB）——长循环里 UIA COM 包装对象（RCW，每秒走树+读属性产生上千个）靠惰性终结释放，PowerShell 长驻进程的经典膨胀。
- 治理两层：① 脚本内每 200 拍（~30s）强制 `GC::Collect + WaitForPendingFinalizers + Collect`，把 RCW 压回去；② watcher 每行 JSON 带上自身私有内存 `ws`（MB，GC 周期测量），Python reader 熔断——**ws>500MB 立即杀掉由守护循环重建**（复用既有重启路径），内存从此有硬上限。
- `parse_watcher_line` 增加 `ws` 字段解析（缺失/坏值归 0），self_check 断言同步更新（空行归一含 ws:0）。
- 验证：self-check 通过；重启后实拍 **34.2 t/s** 正常；watcher 重启 50s 内存 111MB/私有 89MB（健康基线），weberr 无新错误。
- ⚠️ 未验证：GC 对长期曲线的实际压制效果需小时级观察（熔断 500MB 是兜底保证）；熔断触发路径未真实触发过（靠 reader 单元逻辑与既有重启路径覆盖）。

## 性能收尾：pythonw CPU 46%→5% + watcher 孤儿治理（用户问"性能效果"引出的量化排查）

- 量化发现：watcher 本体只有 4% CPU，但主程序 pythonw 烧到 **46% 单核**。基准定位：`detail_data` 一次 **672ms**（500 行 part JSON 解析），push_loop 每秒跑两次（zcode+codex）——历史遗留问题，overlay-only 模式（默认，面板没开）下全是白烧。

## 修"正在运行的会话有时显示 0"（用户反馈）

- 量化定位（正在跑的会话实测）：`message.time_updated` 在回合内**不会持续刷新**（实测停 66s，逼近 90s 归零线），只在工具调用边界偶尔更新——90s 空闲门控用 message 判活，把跑得久（>90s 无新消息行）的运行中会话误判成空闲归零。**part 行才是持续刷新的信号**（实测 5.9s 前仍在写），流式/工具调用都写 part。
- 修复①：`session_last_act` 改为取该会话最新 200 条 part 行的 `MAX(time_updated)`（ORDER BY rowid DESC 走索引尾，实测活跃 0.08ms / 空闲 0.01ms，比逐行 json_extract 方案快百倍）。语义变化：用户消息 part 也算活动（刚发消息=活跃，避免发送后排队期误归零）。
- 修复②（省查询）：门控重排——最近完成请求 <90s 时必然活跃，直接跳过判活查询；只有完成请求超 90s（长回合场景）才查 part 活动。
- 修复③（次因，同症状）：watcher 走树失败（Text 空转）原来会清掉缓存的元素引用 → 后续快路径全空 → 空标题 TTL 4s 到期 → 运行中会话归零。改为：走树一无所获才清引用（防死元素紧循环）；部分失败保留旧引用（留在同一会话时标题照常读出）；快路径读元素抛异常（元素被重渲染换掉）才清。
- 验证：self-check 通过（判活断言改 part 语义：无 part 行 0 / 窗口内命中 / 无会话 0）；重启实拍 **37.7 t/s** 正常，运行中会话 part 判活 27.7s（修复前 message 口径同场景 66s 逼近误杀线）。
- ⚠️ 未验证：长回合（>90s 单次生成、无工具调用）的完整周期未实测（需等真实长回合），但 part 流式写入已被实测证实（5.9s 前仍在写）；走树失败保留引用的路径靠逻辑审查（Text 空转窗口随机，无法按需复现）。

## 最小性能优化：变更检测贯穿全链路（用户要求"以最小性能实现效果"）

- 剩余开销定位：pythonw 5% 里大头是 binder 每拍（0.3s）无条件重算——session_speed_data ~7.7ms + provider_names 0.33ms（后者每次读 2 个配置文件）；watcher 8% 里是快路径 COM 读 + 每 150ms 一行 JSON IO。
- 修复①（binder 脏标记）：`MAX(rowid)` 双查询（model_usage+part，实测 0.2ms，O(1)）作脏标记，标题/模型/DB 都没变就跳过整个重算（含 provider_names）。last_key 在重算成功后才更新——中途异常下一拍自动重试。流式写入时照常重算（est 估算依赖 part），空闲时开销归零。
- 修复②（watcher 输出变更检测）：Emit 内比较上一行，数据没变不发行；走树前心跳带 force 标志强制发（保喂狗，25s 阈值覆盖 12s+ 慢走）。心跳里的 anchor=null 由 binder 粘滞兜底（overlay_anchor 不清空），显示不受影响。
- 修复③：空闲兜底重走 2s→3s（走树主要是 ZCode 侧 provider 负担，降频直接减负； recreated-element 场景切换检测仍 ≤3s，元素稳定时依旧 150ms 级）。
- 实测（重启 1 分钟、流式高峰期）：**pythonw CPU 5%→1.2%**，watcher 7.3%，合计内存 194MB；27.7 t/s 实拍正常，weberr 无新错误。切换会话的响应路径不变（变更立即触发输出+重算）。
- ⚠️ 未验证：空闲长时段的 CPU 曲线（预计 <3%，待用户日常使用观察）；watcher 7.3% 的进一步压缩空间在快路径降频（150→200ms）或 C# 原生重写（~30MB/更低 CPU），当前为保切换响应未做。

## C# 原生 watcher（分支 feature/native-watcher，用户指派）

- 动机：watcher 剩余的 7.3% CPU / 86MB 私有内存是 PowerShell 固有开销（程序集加载、RCW、每行 ConvertTo-Json）。C# 原生版把这块压到最低。
- 实现：`token_watcher.cs`（.NET Framework 4.x，Windows 自带 csc 编译，无需 SDK），**stdout 协议与 PowerShell 版逐字一致**（同 JSON 行：title/model/anchor/ws、变更才发行、走树前强制心跳、TDS_PARENT 父进程自退、走树失败保留引用、自适应兜底 3s/15s）——Python 侧 `parse_watcher_line`/喂狗/熔断/绑定逻辑零改动。
- 接入：`native_watcher_cmd()`——exe 比 .cs 新直接用；否则 GAC 找 UIAutomationClient/UIAutomationTypes/WindowsBase 三程序集 + Framework64 csc 现编译（一次性，缓存 exe）；缺 .cs/缺 csc/编译失败均回退 PowerShell 版。`_watcher_loop` 按 cmd 选择启动 exe 或 PS。
- 编译注意：Git Bash 下 csc 选项用 `-` 前缀（`/r` 会被 MSYS 当路径转换）；`BoundingRectangle` 的 Rect 需要 WindowsBase 引用。exe 8.5KB，已加 .gitignore（构建产物）。
- 实测（重启 1 分钟、流式高峰期）：**watcher 41MB WS / 34MB 私有（PS 版 108/86，内存 -60%），CPU 5.6%（PS 版 7.3%）**；首走 714ms（PS 冷启动 3s+）；主程序 pythonw 0.9%。总占用 142MB / 6.5% 单核。24.3 t/s 实拍正常，weberr 无新错误。
- ⚠️ 未验证：回退 PowerShell 的路径（缺 .cs/缺 csc/编译失败三分支）未实测，仅代码审查；打包（PyInstaller）场景下 exe 落在 dist 目录（frozen 路径 dirname(sys.executable)），首次运行现编译，未跑打包验证；分支待用户验收后合并 main。
