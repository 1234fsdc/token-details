## 二次启动抢焦点修复（单实例）

- 用户反馈"正在用其他窗口时被突然切回 ZCode"。排查确认根因在 `single_instance()`：重复启动（测试脚本反复重启、双击两次快捷方式）会执行 `ShowWindow(SW_RESTORE)+SetForegroundWindow`，而简略面板是启动即创建再隐藏、`FindWindowW` 能找到隐藏窗口——`SW_RESTORE` 会把隐藏面板弹到前台并抢走系统焦点，冗余启动一次抢一次。
- 修复：二次启动改为静默退出（保留互斥体判断，删除 FindWindowW/ShowWindow/SetForegroundWindow）；简略面板由托盘左键唤出，不需要"聚焦已有窗口"。
- 排除项：overlay/简略面板的常规显示与移动路径均带 NOACTIVATE（SW_SHOWNOACTIVATE / SWP_NOACTIVATE），overlay 仅在 ZCode 已是前台时才显示，每秒的 UIA 探测只读不写——均不构成抢焦点源。
- 验证：`--self-check` 通过；真机验证——已有实例持有互斥体时连续两次冗余启动均静默退出（进程消失、无面板弹出），前后 `GetForegroundWindow` 句柄不变；另以 4 进程并发创建互斥体竞态测试，恰好 1 个胜出、3 个 183 退出，机制可靠。
- ⚠️ 未验证/待跟进：① 测试流程存在"同秒双实例共存"现象（互斥体被持有时第二个仍存活），疑与启动瞬间的文件状态有关——与本修复无关，但会让"双实例打架"复现，建议只在干净提交状态启动实例；② weberr.log 显示 ZCode 忙时 UIA 3s 超时成串、00:01:50 曾"ZCode main window not found"，ZCode 自身挂起/重建窗口也可能引发前台跳动，若修复后仍有切走现象，下一步加前台变化记录器（轮询 GetForegroundWindow 记日志）定位。

## overlay 空闲归零（仅 ZCode overlay，简略/详情面板不变）

- 用户问"为什么有的会话结束了还显示速度，有的会话正常停止"：根因是 overlay 的显示规则（当前会话+当前模型+最近 8 条完成请求）没有任何时间衰减——`session_speed_data` 只过滤 status/query_source，不看请求多旧，绑定不断就永远显示（实测 12 天前的会话数据仍返回速度）。而面板是"90s 无活动不显示"（2026-09-11 改定），两套口径不一致。"正常停止"的会话其实是绑定断了（切走/标题读不到超 10 分钟兜底窗口）或当前模型没有 completed 行（手动停止/出错的行不算），不是有停止逻辑。
- 修复（用户改定：只改 ZCode overlay，面板口径不动）：push_loop 在 `session_speed_data` 之后加门控——会话 90s 内无 assistant 活动即置 `zdata=None` → 显示 0。判活用新函数 `session_last_act`（按 `message.time_updated`，同面板 `_last_act` 道理：流式/工具调用期间持续刷新），长回合生成中没有新完成行也不会误归零；只看 assistant 行，用户停留打字不算活动。`session_speed_data` 本体未动。
- self_check 补 3 条断言（取值/无会话返回 0/刷新后命中）。
- 验证：py_compile + self-check 通过；重启实例后 DB 探针——当前会话（assistant 活动 16.8s 前）门控放行、overlay 数据 GLM-5.3-Flash 42.5 t/s；一个 12 天前结束、有速度数据的旧会话被门控归零（正是"结束了还显示"的场景）。capture_overlay 实拍活跃会话 **39.5 t/s**。

## 切换会话提速：常驻 UIA watcher（替代每秒新起 PowerShell）

- 用户要求切换会话后速度显示尽快跟着换。实测定位瓶颈：`zcode_context()` 每次探测 ~1s（进程启动+程序集加载+整树遍历），且**整树 FindAll 遍历本身在 ZCode 流式渲染时可达 12s+**（这也解释了最早的 UIA 超时成串）——push_loop 每秒一次探测，切换会话后最坏 2-3s 才换数，面板刷新也被这个 1s 探测拖住。
- 方案：常驻 PowerShell 观察进程 + Python 守护。首次全量走树后缓存标题/模型/锚点三个 UIA 元素引用，之后每 150ms 只读这 3 个元素的实时属性（~10ms，读的是最新值——会话切换/窗口拖动即时可见）；每 2s 兜底全量重走（WebView2 重渲染换掉元素引用时重建），**兜底间隔自适应**：上次走树 >3s（忙时）拉长到 15s，避免忙时连续 12s 级空走。元素引用失效（抛异常）立即触发重走。走树前先发心跳行，慢走不饿死喂狗。
- Python 侧：`_watcher_loop` 守护线程（无输出 25s 杀掉重启，指数退避；25s 是给 12s+ 慢走留的余量）+ `overlay_bind_loop` 专用绑定线程（0.3s 一拍，原 push_loop 里的粘滞/兜底/空闲归零逻辑原样迁入，db 连接线程私有）。push_loop 不再每秒起新 PowerShell，面板/详情刷新不再被探测阻塞。
- 关键坑（全部实测踩过）：① `uia_watch` 槽位的 ts 跨重启不清零 → 新进程一启动就被喂狗秒杀，PS 进程无限堆积（实测 74 个）——喂狗改用本次 spawn 私有的 `last_line` 时间戳；② `uia_last`/`overlay_anchor`/`overlay_payload` 原是 main() 局部变量，模块级 binder 线程 NameError——提升为模块级；③ 模块缺 `import threading`（原在 main 内局部导入）；④ 草稿态无标题元素时 `te` 恒 null 会让脚本每拍全量走树——归入兜底节奏。
- CacheRequest 批量缓存试过再放弃：`FindAllBuildCache` 在托管包装上不存在，Push/Pop 激活路径能把读值降到 10ms 但 FindAll 本身仍 1-1.8s（瓶颈在 provider 遍历），对忙时无解——不如元素引用快路径。
- 验证：self-check 通过（新增 `parse_watcher_line` 5 条断言：前缀剥离/anchor 容错/bytes 解码/坏行/空行归一）；试跑脚本确认快路径 ~175ms 持续输出最新标题+锚点；重启实例实拍 overlay **26.8 t/s**、定位正确、weberr.log 无新错误；watcher PS 进程 10s CPU 9%（单核，流式高峰期；空闲只有快路径，更低）。切换会话的检测延迟从最坏 ~3s 降到 ≤0.15s（元素稳定时）+0.3s 绑定拍 ≈ **~0.5s 换数**。
- ⚠️ 未验证：真实切换会话的端到端延迟需要用户亲手切（无法在不干扰 ZCode 的情况下模拟）；元素被重渲染换掉时的恢复速度（快路径抛异常→立即重走）只在诊断脚本里验证过分支，未在真实切换里观察。
