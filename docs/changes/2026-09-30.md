# 2026-09-30 简略面板双源同显

## 背景

用户 Codex（kimi-k3）运行中但面板"暂无数据"。诊断：面板此前单源跟随详情下拉（cur_tool，默认 ZCode），ZCode 空闲 90s 即清空——Codex 数据侧完全正常（584 行、token_count 约 22s 一条、格式无漂移、解析零报错），只是面板没在看它。

## 改了什么

- `push_loop`：简略面板改为 ZCode + Codex **双源同时显示**——`detail_data` 跑两遍（zcode 库 + codex 内存库），面板行 = ZCode 行在前 + Codex 行在后；Codex 行 prov 标签本就是 "Codex"，天然区分来源。
- 详情三页语义不变：仍跟随详情窗下拉二选一（`cur_tool`）。
- `--once`/`print_once` 保持 ZCode 单源（调试口，不在本次范围）。

## 已知边界（未改）

- Codex 无 message 表，`running_models` 恒空：运行中可见性靠 token_count 事件落行维持，生成间隙超 90s 该行短暂消失。

## 验证

- `py_compile` + `--self-check` OK。
- 生产库模拟拼接：GLM-5.3-Flash [account:] 38.3 + kimi-k3 [Codex] 16.3，共 2 行。

# 2026-09-30 Codex 速度计算修复（4 t/s 虚低根因）

## 背景

用户报告 Codex 模型速度只有 4 t/s，"绝对不合理"。诊断确认两点根因，均在 `_parse_rollout` 的旧累计差分口径：

1. **分母污染**：旧解析用相邻 token_count 事件间隔做窗口，间隔里含用户空闲（实测 +142 tok 的行窗口 193.6s，其中 182s 是用户打字/读屏）和工具执行时间——模型真实只用了 11.2s（12.7 t/s）。
2. **分子重复计数**：Codex 的 token_count.info.total_tokens 是会话累计值，续接（fork）文件首行会把累计值全量转储一次，旧差分把它当成新增，今日总量虚高到 482M。

## 改了什么（`_parse_rollout` 重写为状态机）

- **分子改用 `info.last_token_usage`**：单次响应的精确用量，天然免除累计转储重复计数；input 仍拆掉 cached。
- **分母改为输入边界窗口**：起点 = 最近输入边界（user 消息 / function_call_output）与上一响应完成的较新者——扣掉用户空闲与工具执行，贴齐 ZCode 的请求级口径（started→completed）。响应在首个输出项出现时定格自己的起点（响应自己尾巴上的 function_call_output 不覆盖它，避免秒完成工具造成 0ms 窗口）。
- **检查点 TC 跳过**：实测 token_count 分两种——带 `last_token_usage` 的在响应完成时发射（结算）；无用量的是检查点 ping（大量存在、且可能先于其响应 item 落盘，文件序不可信），跳过且不动任何状态（不污染 prev_tc、不复位 resp_start）。
- 无起点参照的行 elapsed=0：保留行（今日总量），不计速度。
- `self_check` 伪造 rollout 同步更新：含 user 消息/工具输出边界、背靠背响应、compacted，断言 4 行的起点/窗口/用量。

## 效果（生产数据 2026-09-30 15:19）

- gpt-6-astra：4~12 t/s（虚低）→ **31.3 t/s**（最近 8 条加权 9357 tok / 299.1s）。
- kimi-k3：→ **9.7 t/s**（2119 tok / 218.6s）；单响应窗口实测 11~38s，与手工时间线分析逐一吻合。
- 今日 Codex 总量 482M → **70.7M**（累计转储去重后回落，属修复而非数据丢失）。

## 已知边界（未改）

- 被中断（Esc）的响应没有结算 TC，其部分输出不计入（ZCode 侧cancelled 行有落库，Codex 侧无对应事件）。
- 个别长窗口行（如 +375 tok / 232.9s）是响应内重试或真实慢响应，窗口起点口径下无法进一步拆分。
